Three diagrams of how this configuration library actually runs: how a typed command or a named agent ends up executing, what a tool call has to pass through before it takes effect, and how the four-stage build pipeline moves a plan into reviewed code.

Each is drawn to the mechanism, not the folder listing — read .claude/settings.json or .claude/agents/*.md alongside these if you want the literal source.

01

Two ways a request gets executed

A slash command and a named agent both start with something you type — but one runs inline in this conversation, and the other spawns a separate process with its own memory. That boundary is the whole reason the project keeps skills and agents as different file types.

This is the distinction CLAUDE.md draws between skills and agents in words — the diagram is what that distinction costs and buys: a skill can't forget what you told it three messages ago, but it also can't go run for ten minutes in isolation without cluttering this conversation.

02

What a tool call passes through

Every Write, Edit, Read, or Bash call is intercepted twice: once before it runs, by a guard script that can kill it outright, and — for file edits only — once after, by a syntax check that can't block, only report.

docs/agent-workflow.md's hooks table lists only path_guard.py and syntax_check.py — it predates env_guard.py. .claude/settings.json, drawn above, is the current source of truth.

03

Plan to reviewed code

The four pipeline agents pass one artifact forward at a time: a plan becomes two independent file sets, and both are checked against the same plan they came from.

Nothing in pipeline-reviewer-agent.md triggers a coder automatically on FAIL — the dashed arrow above is a feedback contract (file, line, fix), not a wired loop. Closing it is a next step, not current behavior.
